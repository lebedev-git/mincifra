# План: автоматизация и упрощение подготовки к реестру ПО

Цель — снять с человека рутину и ранние ошибки. 4 направления, разбиты на офлайн-ядро
(низкий риск, без сети) и онлайн-функции (по решению пользователя). Каждое изменение
проверяется отдельно; работаем под git (откат к `2f7b63e`).

## Этап 1. Офлайн-пакет (#1 + #2 + #4) — БЕЗ сети, приоритет

### 1.1 Новый чек: валидация реквизитов (#1)
- Новый файл `02_checks/lib/requisites.js` (по образцу существующих чеков: `run(product) → {id,title,status,summary,findings}`).
- Проверяет по контрольным суммам (детерминированно, офлайн):
  - **ИНН** юрлица (10 цифр, контрольная цифра по алгоритму ФНС).
  - **ОГРН** (13 цифр, контрольная цифра mod 11).
  - Формат дат `rights.rospatentCertificateDate` (ГГГГ-ММ-ДД, реальная дата).
  - Доля РФ-контроля 0–100 и > 50%.
- Пустые поля → SKIP (не FAIL — на ранней стадии карточка неполна).
- Регистрация в `02_checks/checks.js` (5-й чек в массиве `runAllChecks`).
- **Влияние на трекер:** G3 сейчас жёстко ждёт 4 `check`-id. Чтобы не сломать авто-G3,
  новый чек НЕ привязываю к G3 (он про G0/G1). Показывается в отчёте проверок отдельно.
  → уточнение в `tracker.js` не требуется (autoStateFromReport берёт только нужные id).

### 1.2 Pre-flight полноты карточки (#2)
- В `core/` — модуль `readiness.js`: функция `cardCompleteness(product)` → список
  незаполненных обязательных полей (orgName, inn, ogrn, productPageUrl, name, class,
  finance.*), сгруппированных по разделам.
- Отдаётся через API (расширить существующий `submission` или `tracker`, без нового
  роута — переиспользуем один из GET).

### 1.3 Оптимизация уже сделана (#4)
- `buildBuffer` (генерация в памяти) уже внедрён на прошлом шаге — здесь только
  подтверждаю, доп. правок нет.

### 1.4 Экран «Что осталось за вами» (#4-UX)
- Новый view во фронтенде (`app.js`) или блок на дашборде: агрегирует из
  `tracker.buildTracker` + `cardCompleteness` единый список действий человека
  («загрузить правоустанавливающие», «заполнить ИНН», «снять HAR») со ссылками
  на нужные вкладки. Чистый UX-слой, данные уже есть.

**Проверка этапа 1:** `node --check`, прогон `run_checks.js` (новый чек виден),

без регрессий.

## Этап 3. #6 Автозаполнение по ИНН через DaData (ОНЛАЙН, opt-in)

- **Архитектурная граница:** это единственная сетевая функция. Изолирую в отдельный
  модуль `core/egrul.js`; сеть включается ТОЛЬКО при наличии ключа — без ключа
  платформа остаётся офлайн.
- Ключ DaData: env `DADATA_TOKEN` (не хранить в данных/репозитории). Если не задан —
  кнопка «Заполнить по ИНН» скрыта/неактивна с подсказкой.
- Endpoint: `POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/party`,
  заголовок `Authorization: Token <DADATA_TOKEN>`, тело `{"query": inn}`.
  Ответ → `suggestions[0].data`: `name.short_with_opf`→orgName, `ogrn`, `address.value`.
- Новый API-роут `POST /api/products/:id/egrul-lookup` (server-side вызов, ключ не
  утекает в браузер). Таймаут, обработка ошибок сети/лимита/неверного ИНН.
- UI: кнопка рядом с полем ИНН → подставляет orgName/ОГРН/адрес (человек проверяет
  и сохраняет). Данные не считаются истиной — только черновик.

**Проверка:** без ключа — офлайн-режим не изменился; с ключом (если предоставите) —
живой запрос; при ошибке — понятное сообщение, карточка не ломается.

  не трогаются; сеть строго опциональна.
