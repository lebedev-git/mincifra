### Цепочка прав для реестра (Схема B: физлицо → ООО)

Если ПрЭВМ депонирована/зарегистрирована на **автора-физлицо**, а правообладателем в
реестре Минцифры заявляется **ООО**, право должно перейти к ООО и этот переход —
зарегистрирован в ФИПС:

1. **Свидетельство Роспатента** на автора-физлицо (ст. 1262).
2. **Договор отчуждения** исключительного права автор → ООО (ст. 1234) + акт приёма-передачи.
3. **Госрегистрация перехода** права в ФИПС (ст. 1232 п. 2, ст. 1262 п. 5). Обязательна для
   зарегистрированной ПрЭВМ; без неё переход несостоявшийся (ст. 1232 п. 6) → реестр
   Минцифры завернёт заявку по несоответствию правообладателя.

Реестр Минцифры проверяет **факт владения исключительным правом заявителем**, а не
совпадение байтов кода со свидетельством. Расхождение версий кода (свидетельство ≠ текущая
сборка) само по себе не является стоп-фактором; критичен именно разрыв в цепочке прав.
В коде это реализовано статусной машиной `platform/core/rights.js`
(`draft → dep_submitted → dep_granted → assigned → transfer_registered`); подача в Минцифру
открыта только на `transfer_registered`.

Терминология: «реестр отечественного ПО» = **Единый реестр российских программ для ЭВМ и баз данных** (ведёт Минцифры, `reestr.digital.gov.ru`). Отдельно существует реестр ЕАЭС; для 44-ФЗ ключевой — российский.

## 🆕 Изменения ПП № 1236, вступающие в силу с 01.03.2026

Источник изменений — Постановление Правительства РФ № 1937 от 28.11.2025 (опубликовано 08.12.2025), плюс сопутствующее Постановление № 1936 (реестр ПО для собственных нужд) и Федеральный закон № 325-ФЗ от 31.07.2025 (три новых реестра, см. ниже).
Прочитано по вторичным источникам (юридические/консалтинговые обзоры) и частично сверено с фактическим текстом правок к ПП № 1236 (подп. «м» п. 5 Правил). **Перед подачей — сверить с оригиналом акта на pravo.gov.ru/publication.pravo.gov.ru.**

**Статус ресерча: ✅ подтверждено официальным текстом.** Скачан и прочитан официальный PDF Постановления №1937 от 28.11.2025 напрямую с `publication.pravo.gov.ru` (через локальный `curl` — WebFetch-инфраструктура блокируется, вручную обошли через Bash-сессию на машине пользователя). Ниже — дословные формулировки, а не пересказ вторичных источников.

### 1. Обязательная совместимость с ≥2 «доверенными» ОС

Дословно (новый подп. «м» п. 5 Правил): «программное обеспечение совместимо не менее чем с 2 операционными системами, соответствующими требованиям к доверенному программному обеспечению».

Исключения (достаточно 1 ОС) — дословно:
- «правообладатель такого программного обеспечения и правообладатель операционной системы входят в одну группу лиц»;
- «такое программное обеспечение используется исключительно в составе программно-аппаратного комплекса».

Определение совместимости (новый абзац п. 2 Правил, дословно): «"совместимость программного обеспечения с операционными системами" — возможность выполнения программным обеспечением своих функций под управлением операционной системы общего назначения при совместном использовании такого программного обеспечения с техническими средствами без нарушения их корректного функционирования». Понятие «группа лиц» — по ст. 9 ФЗ «О защите конкуренции».

**Поэтапное введение (п. 6 постановляющей части, дословно по категориям):**

| Дата | Категории (дословно из акта) |
| --- | --- |
| 01.09.2026 | «для офисного программного обеспечения» |
| 01.01.2027 | «для программ обслуживания, средств виртуализации, средств обеспечения облачных и распределенных вычислений, средств хранения данных, серверного и связующего программного обеспечения, средств управления базами данных, средств мониторинга и управления, систем контейнеризации и контейнеров, средств разработки программного обеспечения, лингвистического программного обеспечения, средств анализа данных» |
| **01.06.2027** | «для прикладного программного обеспечения, отраслевого прикладного программного обеспечения, средств обеспечения информационной безопасности, средств обработки и визуализации массивов данных» |
| 01.01.2028 | «для промышленного программного обеспечения, средств управления процессами организации» |

> ⚠️ Исправление собственной прошлой ошибки: класс 03 (ИБ) я раньше по вторичным источникам отнёс к волне 01.01.2027 — по факту, дословно, он в волне **01.06.2027**, вместе с прикладным/отраслевым ПО.
>
> Класс 01 (встроенное ПО) в перечне волн не упомянут вовсе — согласуется с тем, что определение совместимости из п.2 применимо только к ПО «под управлением операционной системы общего назначения»; встроенное/RTOS-ПО структурно вне применимости требования, а не просто «отложено».
> Соответствие класса классификатора конкретной волне на уровне подклассов (`NN.NN`) в акте не через коды классификатора, а через текстовые категории — **сверить формулировку с точным подклассом продукта на reestr.digital.gov.ru**.

Для уже включённого в реестр ПО — Минцифры в 6-месячный срок со дня публикации акта утверждает план проверки соответствия (п. 2 постановляющей части).

### 2. Статус «доверенное программное обеспечение» — уточнение сути

Важный нюанс, не увидел бы без первоисточника: требование подп. «м» касается совместимости ПО с ОС, **которые сами являются доверенными** — критерий применяется к ОС, не к самому продукту. Соответствие САМОГО продукта требованиям к доверенному ПО — отдельное, факультативное поле (новый подп. «ц» п. 4: «информация о соответствии программного обеспечения требованиям к доверенному программному обеспечению **(при наличии)**») — то есть не обязательно для базового включения в реестр.

Критерии доверенного ПО/доверенной ОС в самом №1937 не раскрываются — идёт отсылка к ч. 3⁷ и 3⁹ ст. 2 ФЗ «О внесении изменений в ФЗ "О безопасности критической информационной инфраструктуры РФ"».

Практический эффект статуса — преимущество в закупках по ПП № 1875 (правки того же №1937 в него): заявки с ПО без подтверждённого соответствия доверенному ПО приравниваются к заявкам с иностранным ПО.

**Перечень конкретных доверенных ОС в №1937 не приводится и не публикуется централизованно** — по вторичным обзорам, ведётся в ФГИС «Реестр ПО». **СВЕРИТЬ на reestr.digital.gov.ru непосредственно перед подачей**.

### 3. Расследовано и закрыто: удаление фразы в подп. «н» п. 4 — НЕ касается `page_check.js`

Проверил историю подпунктов п.4: подп. «н» — это требование адреса страницы **со сведениями о цене/условиях открытой лицензии**, добавленное в 2015-й акт как раз самим ПП №325 (в 2017 г.). Раз №325 отменяется целиком, чистка фразы в подп.«н» — консеквенциальная правка вслед за отменой №325, не самостоятельное решение.

Требование, которое реально использует пайплайн (`product.productPageUrl` в `page_check.js`/`network_audit.js`/`har_capture.js`) — это **подп. «ж»** («адрес страницы... на которой размещена документация... информация, необходимая для установки и эксплуатации»). Подп. «ж» этим постановлением **не изменяется**. Код трогать не нужно.

### Итог по статусу ПП № 325 (подтверждено официальным текстом)

Приложение к №1937, «Перечень утративших силу актов», п. 1, дословно: «Постановление Правительства Российской Федерации от 23 марта 2017 г. № 325 "Об утверждении дополнительных требований к программам для электронных вычислительных машин и базам данных..."» — признано утратившим силу. №1937 вступает в силу **01.03.2026** (п. 5 постановляющей части) — с этой даты и отмена.

№1937 также правит:
- ПП №1236 (реестр российского ПО) — основной блок, см. выше;
- ПП №658 от 08.06.2018 (централизованные закупки офисного ПО) — убрана ссылка на отменяемое ПП№325, заменена отсылкой на требования к доверенному ПО;
- ПП №1875 от 23.12.2024 (нацрежим при закупках) — заявки без подтверждённого доверенного ПО приравниваются к иностранным (см. выше).

**Практический вывод для пайплайна:** пометку `pp325` в `software_classes.json`/`class_hint.js` после 01.03.2026 читать не как «применяются доптребования ПП№325» (акт не существует), а как исторический индикатор «класс со специфичными требованиями к совместимости с ОС» — актуальная правовая база для класса 06 (и профильных подклассов 02.x) с 01.03.2026 — обновлённое ПП №1236, правило двух доверенных ОС.

### 4. Критерий контроля (дословно, абзац шестой подп. «а» п. 5)

«...находится под контролем Российской Федерации, и (или) субъекта Российской Федерации, и (или) муниципального образования, и (или) гражданина Российской Федерации, и (или) контролируемых ими совместно или по отдельности лиц. При этом под контролем понимается возможность определять решения... в силу наличия права прямо или косвенно распоряжаться более чем 50 процентами общего количества голосов, приходящихся на голосующие акции (доли)...» — то есть подтверждён переход именно на голоса, не на номинальное владение долями.

### 5. Финансовые критерии — два РАЗНЫХ правила, не путать

**А) Новое правило только для гос.-контролируемых правообладателей** (новый подп. «н» п. 5, дословно): применяется, только если правообладатель — «государственная корпорация, государственная компания, публично-правовая компания и иная организация, в уставном капитале которой доля... РФ, субъекта РФ, муниципального образования в совокупности превышает 50 процентов» (или связанная с ними организация). Для них: «доля выручки, полученной... от организаций, входящих в одну группу лиц с правообладателем, не должна превышать 30 процентов общей выручки... за истекший календарный год».

**Б) Классическое правило раскрытия выплат иностранным лицам** (переписанный подп. «с» п. 41, дословно) — то самое, что моделирует `FOREIGN_PAYMENTS_THRESHOLD` в `rules.js`. Формулировка **расширена**: теперь в расчёт явно включаются выплаты «в пользу иностранных юридических лиц и (или) физических лиц, контролируемых ими коммерческих и (или) некоммерческих организаций, **агентов, представителей иностранных лиц и контролируемых ими коммерческих и (или) некоммерческих организаций**» — то есть выплаты через посредников/агентов теперь тоже подлежат учёту, раньше формулировка касалась более узкого круга получателей.

> ⚠️ **Требует внимания в `rules.js`**: если текущая логика `FOREIGN_PAYMENTS_THRESHOLD` анализирует только прямых иностранных получателей (по SBOM/лицензиям), после 01.03.2026 формально в расчёт должны попадать и агенты/представители — сама структура данных для этого может не собираться проектом (нет источника данных о посредниках). Это, скорее, дополнение к дью-дилидженс чек-листу для человека, а не то, что можно детектировать автоматически по текущим артефактам (SBOM/HAR).

Дедлайн ежегодного уведомления об этих сведениях подтверждён дословно — «не позднее 1 июня» (переписанный абзац второй п. 30 и аналогичный п. 67 для реестра ЕАЭС).

### 6. Новые требования для ПАК на базе генеративных моделей ИИ

Производитель (или связанное лицо) должен владеть минимум одним помещением ЦОД в РФ мощностью ≥10 МВт; ПО в составе ПАК — обеспечивать хранение данных ≥1 эксабайта и поддержку задач машинного обучения на 1000+ GPU. Соответствие подтверждается документами. (Актуально только для узкого класса ПАК с генеративными моделями — на большинство продуктов проекта не распространяется.)

## 🆕 Три новых реестра (ФЗ № 325-ФЗ от 31.07.2025, с 01.03.2026)

Дополняют, а не заменяют основной Единый реестр (ПП № 1236). Участие обусловлено конкретными критериями — не обязательны для всех разработчиков.

| Реестр | Для кого | Ключевое условие |
| --- | --- | --- |
| **Реестр значимых разработчиков ПО** | Ключевые IT-компании в приоритетных/стратегических сферах | Контроль РФ/граждан РФ ≥50% голосующих акций + соглашение с Правительством об ОЗП |
| **Реестр ПО для собственных нужд** | Банки, промышленные холдинги с закрытой внутренней разработкой | Легализует использование на объектах КИИ **в обход** основного реестра ПП №1236; рассмотрение правительственной комиссией |
| **Реестр доверенного российского ПО** | Продукты для КИИ, оборонных и госинформсистем | Продукт уже должен быть в основном реестре + проверка ИБ, согласованная с ФСБ/ФСТЭК + 100% исключительных прав без иностранцев |

> Для типового продукта, который готовится через данный пайплайн (стандартная подача в основной реестр), эти три реестра, как правило, **не применимы** — упомянуты для полноты картины и на случай, если у продукта появится КИИ-контекст или гособоронзаказ.

### Как был получен доступ к порталу (для будущих сессий)

`reestr.digital.gov.ru` фильтрует HTTPS (443) для не-российских маршрутов — подтверждено трассировкой (трафик уходил через Франкфурт из-за активного VPN с выходом в Мадрид). Обход: временный точечный `route add` (метрика ниже основного шлюза VPN) на резолвнутые IP портала через обычный домашний шлюз, в обход VPN-туннеля — только с явного разрешения пользователя и с обязательным откатом (`route delete`) сразу после скачивания нужных документов. Не автоматизировать без прямого запроса пользователя каждый раз.
