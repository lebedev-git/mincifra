# Mincifra — архитектура ядра: что это за данные и как это работает

> Документ описывает **ядро системы** — модель данных и бизнес-логику, независимо от
> веб-интерфейса (`platform/web/`). Веб — это тонкий слой над тем, что описано ниже.
> Составлено по факту чтения кода (не по намерениям), дата: 2026-07-03.

## 1. Что это за продукт (одним абзацем)

Локальный инструмент подготовки конкретного программного продукта к включению
в **Единый реестр российского ПО** (Минцифры, ПП РФ № 1236). Он не является клиентом
портала `reestr.digital.gov.ru` (интеграции с ним нет) — это **офлайн-конвейер**:
собирает артефакты кода → автоматически проверяет их на соответствие формальным
критериям реестра → генерирует пакет документов → готовит человеку финальный список
значений и файлов для ручного переноса в форму на портале.

## 2. Модель данных: единица работы — «продукт»

Всё крутится вокруг одной сущности — **продукта** (`store.js`, файловая БД, без СУБД).

```
pipeline/platform/data/
├─ profile.json                     # ЕДИНЫЙ профиль правообладателя (не привязан к продукту)
└─ products/
   └─ <product-id>/                 # id — slug из названия
      ├─ product.json               # КАРТОЧКА — вся анкета продукта (см. §3)
      ├─ tracker.json               # ручные отметки пунктов G0/G1/G2/G4/G5 ({itemId: bool})
      ├─ report.json                # последний результат тех.проверок G3 (см. §4)
      ├─ artifacts/                 # сырые файлы: sbom.json, *.har, dep_*, rights_*
      └─ dossier/                   # сгенерированные .docx (справки, опись, депонирование)
```

Важно: **G3 и GD не хранятся как факт** — при каждом обращении к трекеру они
пересчитываются: G3 из `report.json` (`tracker.js: autoStateFromReport`), GD — из
списка артефактов `dep_*` (`tracker.js: autoStateFromArtifacts`). Это два гейта, где
источник истины — код/файлы, а не ручные отметки человека.

### 2.1. product.json — карточка продукта (главный документ)

```jsonc
{
  "product": {
    "name", "shortName", "version",
    "class": ["04.09"],              // коды из классификатора ПП №1236
    "deliveryType": "SaaS|on-prem|hybrid",
    "guiLanguage": "ru|en",          // ru обязателен — иначе стоп-фактор
    "productPageUrl",
    "description", "purpose",
    "programmingLanguages": [...],
    "expertDemo": { "url", "login", "password" }  // для SaaS — доступ эксперту
  },
  "rightholder": {
    "orgName", "inn", "ogrn",
    "ruControlSharePercent",         // должен быть > 50
    "address",
    "signatory": { "name", "position" }
  },
  "finance": {
    "annualRevenueProduct",          // выручка по продукту за год
    "annualForeignPayments"          // выплаты иностранцам за год — должны быть < 30%
  },
  "tech": {
    "supportedOS": [...], "databases": [...],
    "infraLocation": "RU|иное",
    "sbomFile", "networkEvidenceFile"    // относительные пути в artifacts/
  },
  "support": { "contactFio", "contactEmail", "contactPhone", "hasForeignControl" },
  "rights": { "basis": "rospatent|internal_docs", "rospatentCertificateNumber", "authors": [...] }
}
```

Данные в карточку попадают тремя путями:
1. **Вручную** — форма в UI.
2. **Автозаполнение по коду** (`core/autofill.js` + `core/localsource.js`) — разбор
   `package.json`/README/стека зависимостей локальной папки или ZIP → черновик
   (`patch`), который человек проверяет и сохраняет. Опционально дообогащается LLM
   (`core/llm.js`, только при `ANTHROPIC_API_KEY`).
3. **Автозаполнение реквизитов по ИНН** (`core/egrul.js`, DaData, только при
   `DADATA_TOKEN`) — только `rightholder.orgName/ogrn/address`.

Оба внешних интегратора (LLM, DaData) — **opt-in**: без ключей в `env` система на 100%
работает офлайн на детерминированной логике.

## 3. Процессная модель: гейты G0–G5

Источник истины по смыслу процесса — `pipeline/01_tracker/pipeline_tracker.md`.
Гейты **не линейны** — G0/G1/G2/G4/G5 организационные и готовятся параллельно, G3
считается автоматически из проверок, GD — автоматически из файлов депонирования; оба
не зависят от порядка остальных. GD опционален по закону, но учитывается в проценте.

| Гейт | Кто закрывает | Смысл | Критерий |
|---|---|---|---|
| **G0** Предпосылки | человек | РФ-контроль >50%, УКЭП, ЕСИА, класс ПО, ЕНС-задолженность ≤3000₽ | ручные чекбоксы |
| **G1** Пакет документов | человек | правоустанавливающие + технические документы, SBOM | ручные чекбоксы (частично закрываются генерацией досье) |
| **GD** Депонирование (Роспатент) | **автоматически (по артефактам)** | реферат, акт фиксации SHA-256, фрагмент кода, цепочка прав, заявление, свидетельство | наличие файлов `dep_*` (опц. по закону, но входит в процент) |
| **G2** Страница продукта | человек | публичный URL на РФ-хостинге, контакты ТП, цены | ручные чекбоксы + HAR как доказательство |
| **G3** Техническая готовность | **автоматически** | 5 формальных проверок (см. §4) | `report.overall !== "FAIL"` |
| **G4** Подача на портале | человек | заполнить форму на `reestr.digital.gov.ru`, подписать УКЭП, отправить | ручные чекбоксы |
| **G5** Сопровождение | человек | статус в кабинете, ответы эксперту, приказ Минцифры | ручные чекбоксы |

`tracker.buildTracker(id)` сливает ручные отметки + авто-статус G3 и отдаёт единый
объект: `{ gates[], percent, done, total, hasReport, checksOverall }`. Это единственная
функция, которая знает «на каком мы сейчас шаге» — UI (`topNav`, дашборд) просто её
визуализирует, никакой отдельной логики статуса в вебе нет.

## 4. Автоматическое ядро: G3 — технические проверки

`02_checks/checks.js` — оркестратор, запускает 5 независимых проверок
(`02_checks/lib/*.js`) над карточкой + двумя артефактами (SBOM, HAR). Каждая
проверка возвращает `{ id, title, status: PASS|WARN|FAIL|SKIP, summary, findings[] }`.
Итог (`overall`) = худший статус среди всех.

Бизнес-правила централизованы в `02_checks/lib/rules.js` — единственное место, где
меняются пороги:

| Правило | Значение |
|---|---|
| Порог выплат иностранцам (`foreign_payments.js`) | **< 30%** выручки → FAIL; 25–30% → WARN («запас») |
| РФ-контроль правообладателя | **> 50%** (проверяется в `requisites.js`) |
| Лицензии OSS (`license_scan.js`, вход — CycloneDX SBOM) | critical (SSPL, UNLICENSED…) и high (GPL/AGPL) → FAIL; medium (LGPL/MPL) → WARN; low (MIT/BSD/Apache…) → PASS |
| Сетевой аудит (`network_audit.js`, вход — HAR) | список из ~46 доменов (Google Fonts, GA, AWS/Azure, GitHub CDN и т.д.) → FAIL; белый список `.ru`, Яндекс, VK, Sber Cloud, Selectel → не флагуется; прочие внешние хосты → WARN |
| Страница продукта (`page_check.js`) | GUI обязан быть `ru`; для SaaS обязателен `expertDemo.url`; контакты ТП и описание ЖЦ — WARN, если нет |
| Реквизиты (`requisites.js`) | контрольные суммы ИНН (10/12 цифр) и ОГРН (13/15 цифр) по алгоритму ФНС |

Результат сохраняется в `report.json` и одновременно закрывает пункты G3 в трекере —
это единственная связь между «техническим» и «процессным» слоями системы.

## 5. Генерация документов

Два независимых набора шаблонов `.docx` (общий рендерер — `docx_helpers.js`, единый
стиль Arial/синяя палитра):

- **`03_docs/dossier.js`** (пакет для самой подачи, G1) — 4 документа: Опись,
  Справка о 30%, Архитектурная записка, Соответствие ПП №1236. Все поля подставляются
  из `product.json`; часть текста («ядро продукта — собственная разработка») помечена
  как заполняемая вручную.
- **`03_docs/depon.js`** (депонирование в Роспатент, отдельный юридический трек) —
  5 документов: Реферат, Акт фиксации версии (нужен SHA-256 снимка), Цепочка прав,
  Фрагмент кода (авто-обрезка до 70 страниц, правило «первые 35 + последние 35»),
  Заявление в Роспатент.

## 6. Финальная сборка — «монтажный лист подачи»

`core/submission.js: buildSubmission(id)` — единственное место, где всё
(карточка + отчёт + трекер + досье) сводится в то, что реально нужно человеку в конце:
таблица полей «как есть в форме портала» с кнопками копирования, статус вложений
(готово/вручную), пошаговый сценарий подачи и агрегированный список
«что осталось сделать» (`nextActions`) — сгруппированный по областям (карточка,
артефакты, гейты).

## 7. Сквозной поток данных (от кода к подаче)

```
локальная папка/ZIP проекта
        │  (localsource.js: git archive / zip → SHA-256 → cdxgen SBOM)
        ▼
  autofill.js (+ опц. llm.js) ──► черновик полей product.json ──► человек проверяет/сохраняет
        │
        ▼
  product.json (карточка) + артефакты (sbom.json, *.har)
        │
        ▼
  checks.js (G3, 5 правил) ──► report.json ──► tracker.js закрывает G3
        │                                            │
        ▼                                            ▼
  dossier.js / depon.js (.docx)              tracker.buildTracker (G0-G5, %)
        │                                            │
        └───────────────► submission.js ◄────────────┘
                                │
                                ▼
                  готовые поля + список действий человеку
                                │
                                ▼
                  вручную переносится на reestr.digital.gov.ru
```

## 8. Явные архитектурные решения (и почему)

- **Нет БД** — файловый store с одной точкой доступа (`store.js`); всё остальное
  обращается к данным только через него. Замена на СУБД потребует переписать один файл.
- **Нет обязательных внешних сервисов** — LLM и ЕГРЮЛ/DaData подключаются по ключу
  в `env`, при отсутствии — детерминированная логика без деградации функциональности.
- **G3 не хранит состояние отдельно** — пересчитывается из `report.json` каждый раз,
  чтобы не было рассинхронизации «что реально в отчёте» и «что показано в трекере».
- **Правила проверок вынесены в один файл** (`rules.js`) — пороги (30%, домены,
  лицензии) правятся в одном месте, а не размазаны по проверкам.
- **UI не содержит бизнес-логики** — он только читает `tracker.buildTracker`,
  `submission.buildSubmission`, `report.json` и рендерит; вся логика статусов и
  процентов живёт в `core/`.
