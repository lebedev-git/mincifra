# Mincifra — архитектура ядра: что это за данные и как это работает

> Документ описывает **ядро системы** — модель данных и бизнес-логику, независимо от
> веб-интерфейса (`platform/web/`). Веб — это тонкий слой над тем, что описано ниже.
> Составлено по факту чтения кода (не по намерениям). Дата: 2026-07-03,
> обновлено 2026-09-08 (SQLite-хранилище, движок соответствия ПП № 1236).

## 1. Что это за продукт (одним абзацем)

Локальный инструмент подготовки конкретного программного продукта к включению
в **Единый реестр российского ПО** (Минцифры, ПП РФ № 1236). Он не является клиентом
портала `reestr.digital.gov.ru` (интеграции с ним нет) — это **офлайн-конвейер**:
собирает артефакты кода → автоматически проверяет их на соответствие формальным
критериям реестра → генерирует пакет документов → готовит человеку финальный список
значений и файлов для ручного переноса в форму на портале.

## 2. Модель данных: единица работы — «продукт»

Всё крутится вокруг одной сущности — **продукта**. Доступ к данным идёт только через
`store.js`; структурированные данные лежат во встроенном SQLite (`node:sqlite`), бинарные
файлы — на диске рядом.

```
pipeline/platform/data/
├─ reestr.db                        # SQLite: products, reports, profile, activity, presence
└─ products/
   └─ <product-id>/                 # id — slug из названия
      ├─ artifacts/                 # сырые файлы: sbom.json, *.har, dep_*, reestr_*
      └─ dossier/                   # сгенерированные .docx (справки, опись, депонирование)
```

Таблицы БД: `products(id, data)` — карточка JSON-ом, `reports(product_id, data)` — последний
отчёт проверок, `profile(id=1, data)` — единый профиль установки, `activity` и `presence` —
лента действий и присутствие клиентов. При первом старте, если БД пуста, старая файловая
раскладка (`product.json` / `report.json` / `profile.json`) переносится автоматически.

Важно: **никакой статус не хранится как факт.** Ни ручных отметок, ни поля «стадия».
Чек-лист пересчитывается при каждом обращении из трёх источников: карточка, последний
отчёт проверок, список файлов в `artifacts/`. Поэтому рассинхрон между «отмечено» и
«есть на самом деле» структурно невозможен.

### 2.1. product.json — карточка продукта (главный документ)

```jsonc
{
  "product": {
    "name", "shortName", "version",
    "class": ["04.09"],              // коды из классификатора ПП №1236
    "deliveryType": "SaaS|on-prem|hybrid",
    "guiLanguage": "ru|en",          // ru обязателен — иначе стоп-фактор
    "productPageUrl",
    "description", "purpose",
    "programmingLanguages": [...],
    "expertDemo": { "url", "login", "password" }  // для SaaS — доступ эксперту
  },
  "rightholder": {
    "orgName", "inn", "ogrn",
    "ruControlSharePercent",         // > 50 — по ГОЛОСАМ (п.5 подп.«а», ред. 01.03.2026)
    "stateControlled",               // включает правило 30% по группе лиц (подп.«н»)
    "address",
    "signatory": { "name", "position" }
  },
  "finance": {
    "annualRevenueProduct",          // выручка по продукту за год
    "annualForeignPayments",         // выплаты иностранцам за год — строго < 30%
    "annualRevenueFromGroup"         // выручка от своей группы лиц (только для госкомпаний)
  },
  "tech": {
    "supportedOS": [...], "trustedOs": [...],   // trustedOs — п.5 подп.«м», нужно ≥2
    "databases": [...],
    "infraLocation": "RU|иное",
    "cicdLocation": "RU",                 // п.5 подп.«и» — хранение и компиляция кода
    "licenseKeysLocation": "RU",          // п.5 подп.«к» — лицензионные ключи
    "sbomFile", "networkEvidenceFile"     // относительные пути в artifacts/
  },
  "support": { "contactsRu", "hasForeignControl", "lifecycleDocUrl" },
  "compliance": {                          // заверения заявителя по пункту 5
    "freelyDistributedRu",                 // подп.«б»
    "containsStateSecret",                 // подп.«г»
    "forcedForeignUpdate",                 // подп.«ж»
    "isInfoProtectionSoftware",            // включает подп.«д» и «е»
    "infoSecCertificateNumber", "infoSecLicenseNumber"
  },
  "rights": { "basis": "rospatent|internal_docs", "rospatentCertificateNumber", "authors": [...] }
}
```

Данные в карточку попадают тремя путями:
1. **Вручную** — форма в UI.
2. **Автозаполнение по коду** (`core/autofill.js` + `core/localsource.js`) — разбор
   `package.json`/README/стека зависимостей локальной папки или ZIP → черновик
   (`patch`), который человек проверяет и сохраняет. Опционально дообогащается LLM
   (`core/llm.js`, только при `ANTHROPIC_API_KEY`).
3. **Автозаполнение реквизитов по ИНН** (`core/egrul.js`, DaData, только при
   `DADATA_TOKEN`) — только `rightholder.orgName/ogrn/address`.

Оба внешних интегратора (LLM, DaData) — **opt-in**: без ключей в `env` система на 100%
работает офлайн на детерминированной логике.

## 3. Процессная модель: стадии маршрута

Источник истины по смыслу процесса — `pipeline/01_tracker/pipeline_tracker.md`.
Код: массив `STAGES` в `platform/core/tracker.js` — **порядок массива = порядок маршрута**
(единственный источник). Маршрут выстроен логически «от Роспатента к реестру»: сначала
правовое основание (депонирование → отчуждение → регистрация перехода), затем предпосылки
ООО, продукт, тех.проверки и подача. Чек-лист — проекция данных: пункт закрыт ⟺ его
предикат истинен для {карточка, отчёт, артефакты} (ручных отметок нет).

| # | Стадия (id) | Кто закрывает | Смысл | Критерий |
|---|---|---|---|---|
| 1 | **depon** Депонирование (Роспатент) | **авто (по артефактам)** | реферат, акт SHA-256, фрагмент кода, цепочка прав, заявление, свидетельство | наличие файлов `dep_*` |
| 2 | **assign** Отчуждение права (физлицо → ООО) | **авто (по артефактам)** | договор отчуждения (ст. 1234) + акт приёма-передачи | наличие `dep_assign_contract`/`_act` |
| 3 | **register** Регистрация перехода в ФИПС (ст. 1232) | **авто (по факту)** | заявление о регистрации отчуждения + отметка регистрации перехода (ст. 1232, 1262 п.5) | `dep_assign_register` + `rights.transferRegistered` |
| 4 | **card** Предпосылки подачи | человек | УКЭП, ЕСИА, отсутствие долга на ЕНС свыше 3000 ₽ | предикаты по карточке |
| 5 | **pp1236** Требования к ПО | **авто (из выписки акта)** | ПП № 1236 п. 5, подп. «а»–«н» | правила из `99_reference/pp1236.json` |
| 6 | **record** Сведения реестровой записи | **авто (из выписки акта)** | ПП № 1236 п. 4: название, ОКПД2, класс, URL страницы, основания права, цена | правила из выписки |
| 7 | **attach** Приложения к заявлению | **авто (по артефактам)** | ПП № 1236 п. 11, подп. «а»–«к» | наличие файлов `reestr_*` + демо-доступ |
| 8 | **checks** Артефакты и проверки | **авто** | 5 формальных проверок (см. §4) — доказательная база под критерии | статусы из `report` |
| 9 | **submit** Подача | человек | форма на `reestr.digital.gov.ru`, УКЭП, отправить | предикаты + `prevComplete` |

Стадии 5–7 **не описаны в коде списком** — их пункты приходят из машиночитаемой выписки
акта `99_reference/pp1236.json` через `platform/core/criteria.js`. У каждого пункта есть
ссылка на норму, дословный текст требования и декларативное правило. Правка требований —
это правка выписки, а не кода; поэтому чек-лист сверяется с актом построчно и одинаково
применяется к любому продукту. Пункты со статусом `n/a` (неприменимо) и `pending` (норма
для класса ещё не вступила в силу) видны в списке, но в знаменатель прогресса не входят.

Правовой хребет стадий 1–3 — статусная машина `platform/core/rights.js`
(`draft → dep_submitted → dep_granted → assigned → transfer_registered`). Подача в
Минцифру (`canSubmitReestr`) открыта **только** на `transfer_registered`: переход
исключительного права на зарегистрированную ПрЭВМ обязан быть зарегистрирован в ФИПС
(ст. 1232 п. 2, ст. 1262 п. 5 ГК), иначе он несостоявшийся (ст. 1232 п. 6).

`tracker.buildTracker(id)` пересчитывает все стадии из данных и отдаёт единый объект:
`{ stages[], nextStageId, percent, done, total, hasReport, checksOverall, compliance }`.
Поле `compliance` — сводка сверки с актом: можно ли подписывать декларацию по п. 10
подп. «г» и какие требования пункта 5 этому мешают. Это единственная функция, которая
знает «на каком мы сейчас шаге» — UI (`topNav`, дашборд) просто её визуализирует,
никакой отдельной логики статуса в вебе нет.

## 4. Автоматическое ядро: технические проверки

`02_checks/checks.js` — оркестратор, запускает 5 независимых проверок
(`02_checks/lib/*.js`) над карточкой + двумя артефактами (SBOM, HAR). Каждая
проверка возвращает `{ id, title, status: PASS|WARN|FAIL|SKIP, summary, findings[] }`.
Итог (`overall`) = худший статус среди всех, причём `SKIP` приравнивается к `WARN`: пропущенная проверка — это «нечем проверить», а не «претензий нет».

Бизнес-правила централизованы в `02_checks/lib/rules.js` — единственное место, где
меняются пороги:

| Правило | Значение |
|---|---|
| Порог выплат иностранцам (`foreign_payments.js`) | **< 30%** выручки → FAIL; 25–30% → WARN («запас») |
| РФ-контроль правообладателя | **> 50%** (проверяется в `requisites.js`) |
| Лицензии OSS (`license_scan.js`, вход — CycloneDX SBOM) | critical (SSPL, UNLICENSED…) и high (GPL/AGPL) → FAIL; medium (LGPL/MPL) → WARN; low (MIT/BSD/Apache…) → PASS |
| Сетевой аудит (`network_audit.js`, вход — HAR) | список из ~46 доменов (Google Fonts, GA, AWS/Azure, GitHub CDN и т.д.) → FAIL; белый список `.ru`, Яндекс, VK, Sber Cloud, Selectel → не флагуется; прочие внешние хосты → WARN |
| Страница продукта (`page_check.js`) | GUI обязан быть `ru`; для SaaS обязателен `expertDemo.url`; контакты ТП и описание ЖЦ — WARN, если нет |
| Реквизиты (`requisites.js`) | контрольные суммы ИНН (10/12 цифр) и ОГРН (13/15 цифр) по алгоритму ФНС |

Результат сохраняется в таблице `reports` и одновременно закрывает пункты стадии «Артефакты и проверки» —
это единственная связь между «техническим» и «процессным» слоями системы.

## 5. Генерация документов

Два независимых набора шаблонов `.docx` (общий рендерер — `docx_helpers.js`, единый
стиль Arial/синяя палитра):

- **`03_docs/dossier.js`** (пакет для самой подачи, G1) — 4 документа: Опись,
  Справка о 30%, Архитектурная записка, Соответствие ПП №1236. Все поля подставляются
  из `product.json`; часть текста («ядро продукта — собственная разработка») помечена
  как заполняемая вручную.
- **`03_docs/depon.js`** (депонирование в Роспатент, отдельный юридический трек) —
  5 документов: Реферат, Акт фиксации версии (нужен SHA-256 снимка), Цепочка прав,
  Фрагмент кода (авто-обрезка до 70 страниц, правило «первые 35 + последние 35»),
  Заявление в Роспатент.

## 6. Финальная сборка — «монтажный лист подачи»

`core/submission.js: buildSubmission(id)` — единственное место, где всё
(карточка + отчёт + трекер + досье) сводится в то, что реально нужно человеку в конце:
таблица полей «как есть в форме портала» с кнопками копирования, статус вложений
(готово/вручную), пошаговый сценарий подачи и агрегированный список
«что осталось сделать» (`nextActions`) — сгруппированный по областям (карточка,
артефакты, гейты).

## 7. Сквозной поток данных (от кода к подаче)

```
локальная папка/ZIP проекта
        │  (localsource.js: git archive / zip → SHA-256 → cdxgen SBOM)
        ▼
  autofill.js (+ опц. llm.js) ──► черновик полей product.json ──► человек проверяет/сохраняет
        │
        ▼
  product.json (карточка) + артефакты (sbom.json, *.har)
        │
        ▼
  checks.js (5 правил) ──► reports ──► criteria.js ──► tracker.js
        │                                            │
        ▼                                            ▼
  dossier.js / depon.js (.docx)         criteria.js → tracker.buildTracker (%)
        │                                            │
        └───────────────► submission.js ◄────────────┘
                                │
                                ▼
                  готовые поля + список действий человеку
                                │
                                ▼
                  вручную переносится на reestr.digital.gov.ru
```

## 8. Явные архитектурные решения (и почему)

- **Одна точка доступа к данным** — `store.js`; всё остальное обращается к данным
  только через него. Под ним встроенный SQLite (`node:sqlite`) без внешних зависимостей;
  бинарные артефакты остаются файлами на диске, в БД не переносятся.
- **Критерии — данные, а не код** — требования ПП № 1236 лежат дословной выпиской в
  `99_reference/pp1236.json` с декларативным правилом на каждый пункт. Код (`criteria.js`)
  умеет только вычислять правила. Иначе норму нельзя сверить с актом построчно, а любая
  правка требований превращается в правку логики.
- **Нет обязательных внешних сервисов** — LLM и ЕГРЮЛ/DaData подключаются по ключу
  в `env`, при отсутствии — детерминированная логика без деградации функциональности.
- **Ни одна стадия не хранит состояние отдельно** — всё пересчитывается из карточки,
  отчёта и списка артефактов при каждом обращении, чтобы не было рассинхронизации
  «что есть на самом деле» и «что показано в трекере».
- **Пропущенная проверка не даёт зелёный итог** — статус `SKIP` тянет свод в `WARN`:
  без SBOM и HAR молчат ровно те две проверки, которые ловят стоп-факторы.
- **Правила проверок вынесены в один файл** (`rules.js`) — пороги (30%, домены,
  лицензии) правятся в одном месте, а не размазаны по проверкам.
- **UI не содержит бизнес-логики** — он только читает `tracker.buildTracker`,
  `submission.buildSubmission`, отчёт проверок и рендерит; вся логика статусов и
  процентов живёт в `core/`.
